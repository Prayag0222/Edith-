# EDITH UI — Technical Architecture & Developer Guide

**Subsystem:** EDITH Presence UI v3  
**Project root:** `D:\Edith`  
**Frontend directory:** `D:\Edith\edith-ui`  
**Runtime host:** Python + pywebview on Windows  
**Frontend stack:** React 18, Vite 6, Tailwind CSS 4, Canvas 2D  
**Audience:** Developers maintaining, debugging, building, or extending the EDITH desktop interface

> **Source of truth:** This document describes the checked-out implementation. If source code and this guide differ, source code is authoritative. The UI is a visual and status layer; voice capture, wake-word detection, conversation logic, LLM responses, memory, and TTS remain in the Python application.

---

## 1. Purpose and scope

The UI presents EDITH as a transparent desktop presence. It shows the current assistant state, streamed response text, an animated orb, and a small audio-reactive line.

The UI does not:

- Capture or recognize speech.
- Detect the wake word.
- Decide what the assistant should answer.
- Generate responses or synthesize speech.
- Read or write memory.
- Own the conversation lifecycle.

Those responsibilities stay in the Python application. Python sends state and presentation updates to the frontend through a small JavaScript bridge.

## 2. At-a-glance architecture

```text
Start_EDITH.bat
       |
       v
Python application (app.main)
       |
       +--> EdithUIController
       |         |
       |         v
       |   EdithDesktopWindow (pywebview / Edge WebView2)
       |         |
       |         | window.edithSetState(...)
       |         | window.edithAppendResponse(...)
       |         | window.edithSetAudioLevel(...)
       |         v
       |   React UI in edith-ui/dist/index.html
       |         |
       |         +--> StatusIndicator
       |         +--> ResponseDisplay
       |         +--> AudioVisualizer (Canvas 2D)
       |         +--> EdithOrb (Canvas 2D)
       |
       +--> Voice, assistant, LLM, memory, and TTS services
              (not implemented by the UI)
```

The Python host creates one native overlay window. The React app runs inside that window and receives updates through registered functions on `window`. It does not make network requests to the Python application.

## 4. Building and running the UI

Run npm commands from the UI package directory:

```powershell
cd D:\Edith\edith-ui
npm install
npm run dev
```

Open the Vite development URL with `?preview` to run the visual preview. The preview cycles through the states and supplies a simulated audio level; it does not connect to the Python voice engine.

Build the production frontend:

```powershell
cd D:\Edith\edith-ui
npm run build
```

Vite writes the result to `D:\Edith\edith-ui\dist`. `app/ui/desktop_window.py` resolves this exact path and opens `dist/index.html` as a local file URL. In the standard repository layout, no separate copy step is needed. The Python application raises `FileNotFoundError` if the production entry file is missing.

To preview the production build with Vite:

```powershell
cd D:\Edith\edith-ui
npm run preview
```

The package currently defines `dev`, `build`, and `preview` scripts; it does not define an npm test or lint script.

### Launching the complete desktop application

`Start_EDITH.bat` expects the project virtual environment at `D:\Edith\.venv` and runs:

```powershell
D:\Edith\.venv\Scripts\python.exe -m app.main
```

The frontend production build must exist before launching the Python application. The Python host runs the assistant in a background thread while pywebview owns the desktop UI event loop.

### Desktop lifecycle and launch modes

`Start_EDITH.bat` is the visible/debug launcher. `start_edith.vbs` starts
that same batch file in hidden mode; Python output is appended to
`%LOCALAPPDATA%\EDITH\logs\edith.log`. The application acquires a Windows
named mutex before initializing audio, TTS, memory, or the desktop window, so
a second launch exits without opening another microphone stream.

Closing the overlay's native window hides it and keeps the assistant and
pywebview event loop running. Voice commands `sleep`, `stop`, `go to sleep`,
and `exit` return to wake-word mode and hide the overlay. `hibernate` also
releases the cached Whisper model while preserving the microphone and wake
detector; the model is loaded lazily after the next wake. After the configured
inactivity period, the same Whisper-only hibernation happens automatically.
The default is 300 seconds and can be changed with
`EDITH_HIBERNATE_AFTER_SECONDS`.

Only the exact command `shutdown EDITH` performs a full shutdown. It lets the
goodbye speech finish, closes the UI and backend services, then releases the
single-instance guard. Closing the window is intentionally not a shutdown
action.

## 5. Frontend startup

### 5.1 HTML and React entry

`index.html` provides the `#root` mount point and loads the Manrope and DM Mono fonts from Google Fonts, with local CSS fallbacks. If those font URLs are unavailable, the UI continues to render using system fallback fonts.

`src/main.jsx` imports the global stylesheet, creates a React root in `#root`, and renders `App` inside `React.StrictMode`.

### 5.2 App-level state

`App.jsx` maintains one snapshot:

```js
{
  state: "SLEEPING",
  response: "",
  visible: false
}
```

It registers the bridge functions, subscribes to snapshots from `edithBridge.js`, and passes those values to `EdithInterface`.

When opened with `?preview`, `App` cycles through READY, LISTENING, THINKING, and SPEAKING, changes state about every 5.5 seconds, and simulates an audio level. This mode is for visual inspection only; its timing is independent of real conversation timing.

## 6. Python desktop host

`EdithDesktopWindow` owns the native window and the boundary between Python and JavaScript.

### 6.1 Window configuration

The current host configuration is:

- Fixed size: 560 × 240 pixels.
- Positioned near the top-right of the primary display using a 24-pixel right margin and 32-pixel top margin.
- Frameless, topmost, non-resizable, and created without taking focus.
- Transparent WebView/page background.
- Windows extended styles for tool-window, no-activation, and click-through behavior.

The window uses a near-black `#010101` background as a chroma key. The WinForms host applies a matching transparency key and sets the WebView2 default background to transparent. The UI's page and root backgrounds are also transparent; all of these layers need to remain compatible for the desktop to show through.

The Windows overlay configuration relies on the native pywebview window handle and the Edge/WebView2 renderer. `INTEGRATION.md` contains additional host-specific notes. The UI is not a standalone cross-platform desktop window.

### 6.2 Load and bridge readiness

The host opens the built `dist/index.html` using a local file URL. When the page loads, the host applies native window styles on a daemon thread and checks that all required JavaScript bridge functions exist.

The bridge readiness check waits up to `BRIDGE_TIMEOUT` (10 seconds). Calls made before readiness wait for that event; failures are logged rather than silently treated as a successful UI update.

### 6.3 State controller

`EdithUIController` coordinates visibility and state:

- `activate(state)` cancels a pending hide, shows the window, and sets the requested state.
- `set_state(state)` sends a state change only when it differs from the controller's current state.
- `sleep()` sets SLEEPING and schedules a hide after 0.55 seconds to allow the CSS fade to complete.
- `close()` cancels the hide timer and closes the desktop window.

The React page also fades its presence container on state visibility changes. The controller's delayed hide gives that transition time to finish.

## 7. Python-to-JavaScript bridge

`src/bridge/edithBridge.js` registers the following functions on `window`:

| JavaScript function | Python wrapper | Purpose |
|---|---|---|
| `window.edithSetState(state)` | `EdithDesktopWindow.set_state` | Change the UI state |
| `window.edithSetResponse(text)` | `EdithDesktopWindow.set_response` | Replace displayed response text |
| `window.edithAppendResponse(chunk)` | `EdithDesktopWindow.append_response` | Append a streamed response chunk |
| `window.edithClearResponse()` | `EdithDesktopWindow.clear_response` | Clear the response explicitly |
| `window.edithSetAudioLevel(level)` | `EdithDesktopWindow.set_audio_level` | Set a normalized visual audio level |

Python serializes text and state arguments with `json.dumps` before constructing JavaScript calls. The desktop wrapper validates states, bounds audio level to 0.0–1.0, waits for bridge readiness, and logs JavaScript communication errors.

### 7.1 State store and React updates

The bridge owns a small mutable `edithLiveStore` used by Canvas animation loops. It contains:

- `state`
- `audioLevel`
- `wakePulseAt`

Separately, the bridge maintains a React-friendly current state, response, and listener set. `subscribeEdithUI` immediately sends the latest snapshot to a new subscriber, then returns an unsubscribe function. `App` uses this snapshot to render the components.

The Canvas components read the mutable live store directly so audio/state animation does not require a React re-render on every animation frame.

### 7.2 Response lifecycle

- `setEdithResponse` replaces the current response.
- `appendEdithResponse` adds a streamed chunk to the current response.
- `clearEdithResponse` clears it immediately.
- There is no timed response fade/clear.
- A transition into LISTENING clears the displayed response. Repeating LISTENING while already in LISTENING does not clear it again.
- The Python response loop also explicitly clears the previous response before generating a new answer.

`ResponseDisplay` scrolls to the newest streamed text and uses a polite live region for screen readers.

### 7.3 Audio level

`setEdithAudioLevel` ignores non-finite values and clamps finite values to 0.0–1.0. The orb and audio line use this value for visual reactivity.

The JavaScript bridge and Python window wrapper expose this capability, but the current Python application does not call `set_audio_level` with measured microphone or TTS samples. The `?preview` mode generates a simulated value. As a result, preview reactivity is simulated; do not describe it as measured live voice amplitude.

## 8. Assistant state lifecycle

The frontend accepts these states:

| State | Meaning in the interface |
|---|---|
| SLEEPING | Presence is faded out; the desktop controller hides the window after its short transition delay |
| READY | Standby/ready presentation |
| LISTENING | EDITH is receiving a user utterance or waiting for the next turn |
| THINKING | The backend is processing the recognized request |
| SPEAKING | EDITH is producing spoken output |

Typical voice interaction:

```text
SLEEPING
  -> LISTENING    wake word detected; overlay shown
  -> THINKING     utterance transcribed; request processing begins
  -> SPEAKING     response text streams and TTS plays
  -> LISTENING    playback cleanup completes; another utterance can be heard
```

No-speech timeout or the explicit `sleep` voice command returns EDITH to wake-word mode. The Python side sets SLEEPING; the UI transitions out and is hidden by the state controller. The next wake event activates the overlay again.

This state sequence is driven by the Python application, not inferred by React. If the Python state update is missing or out of order, the frontend cannot determine the actual voice-engine state on its own.

## 9. React component guide

### 9.1 `EdithInterface`

`EdithInterface` is the layout shell. It applies the state and visibility classes, then arranges:

- Left column: status, response, and audio line.
- Right column: orb and EDITH identity mark.

It does not own assistant state or make bridge calls.

### 9.2 `StatusIndicator`

Maps the current state to a readable uppercase label and renders the EDITH mark and subtitle. Unknown state values fall back to READY for the label; the bridge and Python host separately restrict accepted states.

### 9.3 `ResponseDisplay`

Displays streamed response text when present. Otherwise it can show fallback copy for READY, LISTENING, or THINKING. It scrolls to the latest response text as chunks arrive.

The current transcript area is 128 pixels high, scrollable, and uses 15-pixel, medium-weight, high-contrast text. Its bottom is not faded by a mask. Longer responses can be read by scrolling inside the transcript area.

### 9.4 `AudioVisualizer`

Draws a small 2D waveform line on a Canvas and labels the current activity as voice input, voice output, local inference, or standby. It animates while LISTENING or SPEAKING, then allows the waveform to settle.

### 9.5 `EdithOrb`

Draws the main presence orb on a transparent Canvas. It reads state and audio values from `edithLiveStore`, interpolates toward the current state's visual parameters, and delegates individual drawing layers to `orbLayers.js`.

It resizes through `ResizeObserver`, caps device-pixel ratio at 1.5, pauses when the document is hidden, and stops its animation loop after the orb has faded to SLEEPING.

## 10. Canvas and visual engine

### 10.1 State configuration

`orbConfig.js` defines opacity, scale, ring and particle speeds, core and aura intensity, scan alpha, audio weight, and colors for each supported state. The animation loop interpolates current values toward these targets rather than switching abruptly.

The orb uses a fixed pool of 22 particles in the current component configuration. The pool is created once for the component rather than recreated on every animation frame.

### 10.2 Drawing layers

`orbLayers.js` contains Canvas drawing functions for:

1. Atmospheric radial glow.
2. Dotted orbital paths.
3. Rotating technical rings and tick marks.
4. Sweeping scan arcs.
5. Orbital particles and halo points.
6. Wake activation ripple and speaking pulses.
7. Inner translucent sphere.
8. Central energy core.

These are Canvas 2D drawings, not a 3D scene. The UI does not use WebGL or Three.js.

### 10.3 Animation helpers

`lerp.js` provides:

- `damp`: time-based exponential interpolation.
- `clamp`: constrain a number to a range.
- `easeOutCubic`: easing used by the wake ripple.

The orb caps frame delta to reduce large jumps after pauses. The Canvas backing resolution is capped to limit high-DPI rendering cost.

## 11. Layout, styling, and transparency

`styles.css` combines Tailwind CSS with custom classes for the overlay and Canvas components.

- `html`, `body`, and `#root` fill the viewport and remain transparent.
- The presence container fades and scales between visible and sleeping states.
- The left text column is constrained to avoid covering the orb.
- The transcript has a fixed scroll region and hidden scrollbar.
- State-specific accents update the identity mark and orb presentation.
- The stylesheet includes a `prefers-reduced-motion` rule for CSS animation and transition durations.

The source HTML loads Manrope and DM Mono externally. The CSS specifies fallback fonts so network access is not required for the rest of the interface.

The visual overlay depends on transparency at several layers: page CSS, WebView2's default background, and the native Windows form's transparency configuration. A black or opaque rectangle is normally a host/renderer/transparency-key problem, not an orb-rendering problem.

## 12. Performance and accessibility

Current performance choices include:

- Canvas 2D rather than a 3D graphics framework.
- A fixed, low-count particle pool.
- Device-pixel ratio capped at 1.5 for the orb and audio line.
- Animation paused while the document is hidden.
- The orb loop stops after the sleeping fade completes.
- Mutable animation state avoids React updates on every Canvas frame.

Accessibility support includes a polite live region for response text and a descriptive `aria-label` on the orb Canvas. The UI is primarily a visual desktop overlay and does not provide a complete keyboard-driven control surface.

## 13. Development and verification workflow

1. Make source changes under `edith-ui/src/` or the UI host under `app/ui/`.
2. Run the Vite development server and use `?preview` to inspect static visual states.
3. For bridge or lifecycle changes, validate them through the actual Python/pywebview application; preview mode does not exercise Python integration.
4. Build the production assets:

   ```powershell
   cd D:\Edith\edith-ui
   npm run build
   ```

5. Confirm `edith-ui/dist/index.html` exists, then launch `Start_EDITH.bat`.
6. Verify wake display, response streaming, sleep/hide, close-to-hide, and explicit `shutdown EDITH`.

`npm run build` checks the Vite/React/CSS production compilation. It does not test microphone capture, WebView2 transparency, Python-to-JavaScript timing, real TTS amplitude, or multi-monitor placement.

## 14. Safe extension checklist

### Adding a new state

Review all state-dependent locations together:

- `VALID_STATES` in `src/bridge/edithBridge.js`.
- The allowed-state set in `EdithDesktopWindow.set_state`.
- State labels in `StatusIndicator.jsx`.
- Visual parameters in `ORB_STATES` in `orbConfig.js`.
- Any state-specific CSS in `styles.css`.
- Preview controls and sequence in `App.jsx`, if useful.
- Python orchestration and UI-controller behavior.

Do not add a frontend-only state that the Python host rejects.

### Adding or changing a bridge function

Update the full path consistently:

1. Export/register the function in `edithBridge.js`.
2. Include it in `EdithDesktopWindow`'s bridge readiness check.
3. Add a Python wrapper method that calls it through `_execute_js`.
4. Add an actual producer/call site if the function needs runtime data.
5. Remove the registered global during bridge cleanup.

For text or other payloads, preserve JSON serialization rather than interpolating raw values into JavaScript.

### Changing response visibility

Response visibility has two relevant owners:

- `edithBridge.js` controls response state and when it is cleared.
- `ResponseDisplay.jsx` and `styles.css` control how that state is shown.

The Python application also calls `clear_response()` before generating a new answer. Check all three before changing persistence or clearing behavior.

## 15. Troubleshooting

### Python reports that the production UI build is missing

Run `npm run build` from `D:\Edith\edith-ui` and verify `dist/index.html` exists. The host resolves the path relative to `app/ui/desktop_window.py`.

### The native window is opaque or has a black background

Confirm that the Edge/WebView2 renderer is active, the WebView2 Runtime is installed, page backgrounds remain transparent, and the native transparency key still matches the configured `#010101` key. Check Python logs for the renderer and transparency messages.

### Python state changes do not affect the React page

Check that the page loaded from the expected production build, all required `window.edith...` functions were registered, and the Python log reports JavaScript bridge readiness. The host waits up to 10 seconds for the bridge.

### Response text clears unexpectedly

Check for an explicit `clear_response()` call in Python and for a transition into LISTENING in `edithBridge.js`. The bridge no longer applies a time-based clear.

### Audio reactivity is present in preview but not in the live application

Preview mode simulates audio level. The Python wrapper exists, but the current application has no call site sending measured audio levels. This requires a deliberate data source and integration; do not substitute room microphone amplitude for TTS playback amplitude.

### Orb does not animate

Check that the current state is not SLEEPING, the document is visible, the Canvas has non-zero dimensions, and the browser supports Canvas 2D and `ResizeObserver`.

## 16. Known limitations and non-goals

- The UI is designed around one fixed-size Windows desktop overlay.
- The frontend does not own voice or conversation state.
- Audio amplitude is not currently connected to measured live Python audio.
- The preview is synthetic and cannot validate the native desktop host.
- The UI has no npm test or lint command in its package scripts.
- External Google Fonts may fall back to local fonts when unavailable.
- A production build is required before the Python host can open the UI.
